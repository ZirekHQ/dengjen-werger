= Architecture

This is the living, current-state summary of how Dengjen Werger is built.
Unlike the dated design docs under `docs/superpowers/specs/` and
`docs/superpowers/plans/` (point-in-time records, not edited after the
fact), this file is expected to change whenever the actual architecture
does. For the full reasoning behind these choices, see
link:docs/superpowers/specs/2026-09-11-dengjen-werger-design.md[`docs/superpowers/specs/2026-09-11-dengjen-werger-design.md`].

== Backend layering (ports &amp; adapters)

----
src/main/java/werger/
├── domain/    records, enums, sealed WorkItemStatus — pure data + state machine, zero I/O
├── ports/     TranslationSource, MachineTranslationSource, Result, SourceError, MtError
│                                    — interfaces the domain depends on
├── adapters/
│   ├── crowdin/         CrowdinClient + response records (RestClient) — implements TranslationSource
│   ├── googletranslate/ GoogleTranslateClient, GoogleTranslateSource + response records
│   │                    — implements MachineTranslationSource
│   └── db/              Db, DbConfig                             — HikariCP pool over pgjdbc
├── service/   DraftCredit           — pure: scores a submission against its machine-translated draft
├── http/      HealthController      — HTTP entrypoints, calls into domain/ports
└── WergerApplication                — Spring Boot entrypoint and composition root
----

Dependency rule: `domain` never imports from `adapters` or `http`, and
never performs I/O. `ports` defines the interfaces both `domain` logic and
`adapters` are written against — it's the only thing an adapter and the
domain have in common. `http` and the Spring configuration are the only places allowed to
know about a concrete adapter; everything else programs against the port.
There is no dependency-checker enforcing this yet (see Open gaps below) —
it's enforced by convention and PR review only.

== Key decisions and why they're not obvious from the code

* *JDBC + HikariCP* for Postgres access — the Spring ecosystem default.
 (The earlier Scala build used Skunk specifically to avoid JDBC under
 GraalVM native-image; Spring Boot's AOT processing supports pgjdbc and
 HikariCP in native images, so that constraint no longer applies.)
* *Supavisor transaction pooler (port 6543), not the direct port.* In
 transaction-pooling mode a backend connection is handed out per
 transaction, not per session, so named server-side prepared
 statements can collide or go missing across pooled connections. This was
 a verified risk, not a hypothetical — `DbConfig.jdbcUrl()` sets
 `prepareThreshold=0` to stop pgjdbc from ever creating one; check it
 before changing pooling or statement behavior.
* *One `TranslationSource` port, one implementation (`CrowdinSource`,
 in progress).* The trait's shape is set by Crowdin's real API, not
 speculative multi-backend support — see the port doc comment.
* *`MachineTranslationSource` (Google Translate adapter) is built but not
 yet wired in.* It fills `WorkItem.targetTextDraft` and (via
 `DraftCredit`) can distinguish confirming a draft as-is from real
 translation work, but nothing yet calls it — that happens once
 `JobsService` (the Crowdin sync job) and `ApprovalService` (points
 award) exist. See
 link:docs/superpowers/specs/2026-09-12-mt-draft-assist-design.md[`docs/superpowers/specs/2026-09-12-mt-draft-assist-design.md`].
* *GraalVM native-image on Cloud Run* remains the target, chosen for
 cold-start latency given request-driven (not always-on) traffic. The
 build ships a JVM image today (see `Dockerfile`); a native build via
 Spring Boot AOT and the GraalVM Native Build Tools plugin is not wired
 in yet. Check native-image compatibility before adding a library that
 does reflection or loads native code.
* *80% line coverage is a hard CI gate* (`jacocoTestCoverageVerification`
 in `build.gradle.kts`, run by `./gradlew check`), with
 `WergerApplication` and `Db` excluded — a composition
 root and a thin driver wrapper aren't meaningfully unit-testable, and
 including them would just pressure someone into padding coverage with
 low-value tests elsewhere.
* *Three test tiers* (Gradle test suites `test`, `integrationTest`, `e2e`) map to three
 trust levels of dependency — stubbed, real dev infra, real third-party
 API — not to a generic "small/medium/large" split. Full rationale and the
 skip-when-credentials-are-absent requirement live in
 link:.github/CONTRIBUTING.adoc[`.github/CONTRIBUTING.adoc`].

== Explicit non-goals (v1)

* Multiple `TranslationSource` adapters. Crowdin is the only one; later
 adapters (`NvdaOmegatCsvSource`, Launchpad, GNOME, KDE, Mozilla Pontoon)
 are phased in link:ROADMAP.adoc[`ROADMAP.adoc`], each contingent on that
 platform accepting automated contributions at all.
* Languages beyond Kurmanji. `Language` is a first-class field throughout
 the domain model specifically so this isn't a rewrite later, but no
 second language is seeded in v1.
* A separate frontend build pipeline or framework decision — deferred to
 the implementation plan, low-stakes.

== Open gaps

No automated architecture fitness function exists yet (no ArchUnit
rule enforcing the `domain` → `ports` → `adapters` dependency direction).
Layering is currently held by discipline and PR review only — worth
adding an ArchUnit test once the adapter count grows past one.
